## Two processes, one panel

Like any VS Code extension, this runs as two separate JavaScript contexts that only talk through `postMessage`:

- **Extension host** (`src/extension.ts`, `src/treePanel.ts`'s `HarnessTreePanel` class, `src/transcriptWatcher.ts`, `src/harness.ts`, `src/sidebarView.ts`) — real Node.js, has filesystem/`vscode` API access.
- **Webview client** — the inline `<script>` block generated by `renderHtml()` in `treePanel.ts`. No Node, no `vscode` API — only what `acquireVsCodeApi()` and the DOM give it.

## Startup sequence

1. `activate()` in `extension.ts` registers the three commands and the sidebar view provider, then calls `HarnessTreePanel.createOrShow(rootPath)` unconditionally — the tree panel opens on every activation, no user action required.
2. `HarnessTreePanel`'s constructor calls `this.refresh()` *before* constructing the `TranscriptWatcher` — the webview's script (and its `message` listener) must be loaded before the watcher can post anything, or the earliest `step`/`debug` messages are silently dropped.
3. `refresh()` calls `buildHarnessIndex()` (in `harness.ts`) to walk the real workspace directory tree, `serialize()` to flatten it into the flat `VizNode[]` list the client actually receives, and `readCollapseConfig()` to read the four `aharVisualizer.max*` settings — both get JSON-stringified straight into the HTML template (`const nodes = ${data}; const config = ${configData};`).
4. The `TranscriptWatcher` starts polling on its own interval (`aharVisualizer.rescanIntervalMs`, default 400ms) and pushes events into the panel via the three host→webview message types below.

## The message protocol

**Host → webview** (`panel.webview.postMessage(...)`):

| `type` | Payload | Sent when |
|---|---|---|
| `step` | `{ step, filePaths }` | `TranscriptWatcher` processes one or more new transcript lines in a tick — `filePaths` are the `Read`/`Edit`/`Write` targets extracted from them. |
| `debug` | `{ source: 'host', message }` | Any watcher/host-side event worth showing in the in-panel debug log. |
| `sessionReset` | *(none)* | The watcher switches to a different session file than before — the client clears all visited/hot state so "recently touched" stays scoped to the session currently running. |

**Webview → host** (`vscode.postMessage(...)`, handled in `HarnessTreePanel`'s `onDidReceiveMessage`):

| `type` | Payload | Effect |
|---|---|---|
| `openFile` | `{ path }` | Opens the file in a real editor tab and reveals it in the Explorer. Used both for real leaf files and for a `HARNESS.md`/routing file folded into its parent directory's color (no node of its own). |
| `refresh` | *(none)* | Re-runs `refresh()` — same as the toolbar's ⟳ button. |
| `clientDebug` | `{ message }` | Relayed into the same debug log / `DEBUG_LOG_PATH` file as host-side debug lines, so both sides land in one unified trail. |
| `openSettings` | *(none)* | Runs `workbench.action.openSettings` scoped to `aharVisualizer`. |

The sidebar (`sidebarView.ts`) is a *separate* webview with its own tiny message pair — `openTreeVisualization` and `openSettings` — that just re-dispatch to the two matching extension commands (`aharVisualizer.openTreeVisualization`, `aharVisualizer.openSettings`) rather than talking to `HarnessTreePanel` directly.

## Why the client script lives inline

There's no bundler in this project — a VS Code webview loads one self-contained HTML string, so the entire client app (thousands of lines: layout, pan/zoom, collapse/expand-by-depth, glow/decay, toolbar, legend, debug log) is a single template literal inside `renderHtml()` in `treePanel.ts`. `test/webviewLogic.harness.js` extracts it verbatim at test time rather than the tests reimplementing any of that logic themselves — see `HARNESS.md`'s Testing section for the extraction markers this depends on.
